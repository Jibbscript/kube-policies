# Key-Management Plan — Kube-Policies (KP)

This Key-Management Plan (KMP) defines how every cryptographic key and secret in
the Kube-Policies system is **generated, distributed, stored, rotated, and
retired**, and the procedure for responding to a suspected key compromise
(SC-12, SC-13, SC-17, SC-28, CM-6). It governs the keys enumerated in the
crypto inventory (`crypto-inventory.md`, CRY-WU-18) and depends on the approved
algorithms in `crypto-standards.md` and the FIPS 140-3 module in
`crypto-module.md`. It is part of the [compliance evidence package](README.md).

> **Posture:** Kube-Policies is a Proof-of-Concept being driven to
> FedRAMP-Moderate readiness; it is **not yet authorized**. The chart's default
> generation paths for the internal bearer token and audit-integrity HMAC key
> are **demo-grade** (template-time RNG, not a FIPS CSPRNG). This plan
> distinguishes the implemented controls from the operator actions still
> required for production, so nothing here is overstated.

This plan is reviewed at least **annually** (next review **2027-05-31**) and
after any key-compromise event or material change to a key's lifecycle. The
System Owner is accountable; key-owner roles referenced below are **TBD until
assigned** (see `roles-raci.md`).

## 1. Scope and key register

The authoritative per-key register — purpose, algorithm, validated module,
storage Secret, owner, rotation interval, and controls — is the crypto
inventory (`crypto-inventory.md`). This plan does not duplicate that table; it
adds the lifecycle **procedures**. The keys in scope are:

1. Webhook serving TLS key (`<release>-admission-webhook-certs`)
2. policy-manager serving TLS key (`<release>-policy-manager-certs`)
3. dashboard serving TLS key (`<release>-dashboard-certs`)
4. mTLS client-CA bundle (`<release>-admission-webhook-client-ca`, public cert only)
5. Internal bearer token (`<release>-internal-token`)
6. Audit-integrity HMAC key (`<release>-audit-integrity`)
7. cert-manager shared root CA (`<release>-ca`)
8. Inherited at-rest KMS key (apiserver `EncryptionConfiguration` / CSP)

(`<release>` = the Helm release / `kube-policies.fullname`.)

## 2. Key generation (SC-12, SC-13)

| Key | Generation method | FIPS CSPRNG? |
|---|---|---|
| TLS serving keys (1–3) + root CA (7) | cert-manager generates the key pair at the configured `algorithm`/`size` (ECDSA P-256 default) when `certManager.enabled=true`. | cert-manager's own crypto (out-of-process); strength pinned to `crypto-standards.md`. |
| Demo TLS keys | `scripts/gen-webhook-cert.sh` (ECDSA P-256, OpenSSL) or sprig `autoGenerate` (RSA-2048, fixed). | **DEMO-ONLY** — never the production path. |
| mTLS client-CA (4) | Operator supplies the apiserver client-CA cert via `admissionWebhook.tls.clientCA`; KP generates no key here (public cert only). | n/a (no secret material). |
| Internal bearer token (5) — **production** | Generate out-of-band with a FIPS CSPRNG and set `internalToken`: `auth.GenerateToken` draws 32 bytes (256 bits) from `crypto/rand` (FIPS DRBG when built with `GOFIPS140`), or `openssl rand -base64 48`. | **Yes** for the operator-supplied path. |
| Internal bearer token (5) — **chart default** | `randAlphaNum 48` (sprig, template-render time). | **No — DEMO-ONLY.** Production must override. |
| Audit-integrity HMAC key (6) — **production** | Operator supplies `audit.integrity.key` (or an external Secret) generated by a FIPS CSPRNG. | **Yes** for the operator-supplied path. |
| Audit-integrity HMAC key (6) — **chart default** | `randAlphaNum 64` (sprig, template-render time). | **No — DEMO-ONLY.** Production must override. |
| At-rest KMS key (8) | Cluster/CSP provisions in an HSM/KMS. | **Inherited** — CSP responsibility. |

**Rule:** for any production deployment, the System Owner confirms that keys 5
and 6 are operator-supplied (not the `randAlphaNum` fallback) before the system
is used as ATO evidence. The chart's template comments label the fallbacks
`DEMO-ONLY` precisely so this gap is auditable.

## 3. Key distribution (SC-12, SC-17, CM-6)

- **TLS serving keys & root CA (1–3, 7):** cert-manager writes each key pair
  into its own Kubernetes Secret in-cluster; the private key **never leaves the
  cluster**. Pods mount the Secret read-only. The shared root CA
  (`issuerType=selfsigned` bootstrap) signs all three leaves so a single mounted
  `ca.crt` verifies every service (`charts/kube-policies/templates/issuer.yaml`,
  `certificate.yaml`).
- **Hot reload:** serving certs are reloaded without a pod restart via
  `internal/tlsreload`, so cert-manager renewals take effect in place.
- **mTLS client-CA (4):** distributed as the public `ca.crt` in
  `<release>-admission-webhook-client-ca`, mounted at `/etc/client-ca/ca.crt`
  and passed via `--client-ca-path`; the webhook enforces
  `RequireAndVerifyClientCert` only when a client-CA pool is present
  (`internal/config/tls.go`).
- **Internal bearer token (5) & audit HMAC key (6):** stored as Opaque Secrets
  and mounted into the consuming pods; the token is shared between
  admission-webhook and policy-manager. Tokens/keys are transmitted only as
  in-cluster Secret mounts — never embedded in images or logs.
- **At-rest KMS key (8):** managed entirely by the cluster/CSP; not distributed
  by KP.

## 4. Key storage (SC-28)

Every KP-managed key is a Kubernetes Secret, each serving cert in its **own**
Secret (`<release>-admission-webhook-certs` / `-policy-manager-certs` /
`-dashboard-certs`). At-rest confidentiality is **inherited** from the cluster's
apiserver `EncryptionConfiguration` (KMS v2 preferred; `secretbox` fallback) —
KP does not encrypt at rest in-process. See `secrets-at-rest.md` for the
enabling steps and verification. The audit-integrity HMAC key is held in memory
as a defensive copy after load (`NewChainer` copies the key bytes;
`internal/audit/integrity.go`).

## 5. Rotation schedule (SC-12)

| Key | Rotation trigger / interval | Mechanism |
|---|---|---|
| TLS serving keys (1–3) | `duration=8760h` (1 year), `renewBefore=720h` (30 days), `rotationPolicy=Always` | cert-manager auto-renews; `internal/tlsreload` hot-reloads the new cert with no restart. |
| Root CA (7) | `duration=43800h` (5 years), `renewBefore=720h` | cert-manager; **rare** — root rotation re-issues every leaf, so schedule a maintenance window. |
| mTLS client-CA (4) | Follows the kube-apiserver client-CA's own lifecycle | Operator updates `admissionWebhook.tls.clientCA` when the apiserver CA rotates. |
| Internal bearer token (5) | No fixed interval pinned in code; recommend **≤ annually** and on personnel change/compromise | **Zero-downtime two-token window:** set the new token as current and the prior token as previous (`POLICY_MANAGER_INTERNAL_TOKEN_PREVIOUS`) so both are accepted during propagation, then drop the old. `TokenVerifier` accepts any configured non-empty token via constant-time SHA-256 compare. Procedure: `docs/runbooks/internal-token-rotation.md`. |
| Audit HMAC key (6) | No fixed interval in code; recommend **≤ annually** and on compromise | Update `audit.integrity.key` (or the external Secret). **Caveat:** rotation starts a **new** hash-chain segment — retain the prior key to `VerifyChain` historical records; do not discard old keys while their records are within retention (`audit.retention`, default 90d). |
| At-rest KMS key (8) | Per CSP/KMS policy | Cluster/CSP; re-encrypt existing Secrets after a provider change (`secrets-at-rest.md`). |

Existing-Secret precedence (`lookup`) in the token and audit-integrity templates
means a `helm upgrade` does **not** silently regenerate a live key — rotation is
an explicit operator action, preserving idempotence.

## 6. Key-compromise response procedure

When a key or secret is suspected or confirmed compromised, the System Owner /
ISSO executes the following (and records it per the incident-response process):

1. **Declare & scope.** Identify which inventory row (`crypto-inventory.md`) is
   affected and what it protects. Treat any exposure of a Secret's contents
   (logs, image, etcd dump, leaked manifest) as compromise.
2. **Internal bearer token (5):** generate a new FIPS-CSPRNG token, install it as
   the **current** token while setting the compromised token as **previous**
   only long enough to let callers pick up the new one, then **remove** the
   compromised token from the previous slot immediately
   (`POLICY_MANAGER_INTERNAL_TOKEN_PREVIOUS` cleared). For active compromise,
   skip the grace window and cut over directly, accepting brief request
   rejections. Procedure: `docs/runbooks/internal-token-rotation.md`.
3. **TLS serving key (1–3):** trigger immediate re-issuance (delete the leaf
   Secret or force cert-manager renewal); `internal/tlsreload` picks up the new
   cert. If the **root CA (7)** is compromised, re-bootstrap the CA (re-issues
   all leaves) and redistribute the new `ca.crt` to every client/`caBundle`.
4. **mTLS client-CA (4):** if the apiserver client-CA is compromised, coordinate
   apiserver CA rotation and update `admissionWebhook.tls.clientCA`.
5. **Audit HMAC key (6):** install a new key. **Preserve** the compromised key
   offline so historical records can still be verified, but treat records sealed
   under a compromised key as **suspect** for tamper-evidence after the exposure
   time; document the cutover sequence number and timestamp.
6. **At-rest KMS key (8):** invoke the CSP/KMS key-compromise/rotation procedure
   and re-encrypt affected Secrets.
7. **Verify & close.** Confirm the new key is live (handshake / `Verify` /
   `VerifyChain` as applicable), confirm the compromised material is no longer
   accepted, capture evidence (`kubectl get secret`, `openssl x509 -text`,
   chain-verify output), and update the POA&M / incident record. Re-run the
   compliance link/format check (`scripts/validate/compliance_check.py`) if
   documentation changed.
