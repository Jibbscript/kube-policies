# Release Verification (SUP-WU-15)

Controls: NIST SR-4, CM-14, SA-10 | SSDF RV.1

This guide explains how to verify the integrity and provenance of a kube-policies
release **before you deploy it**. All trust is anchored to the keyless OIDC
identity of `release.yml` — there is no long-lived public key to distribute
or rotate.

> **Pre-1.0 notice.** This project has not yet cut a signed release tag and the
> working branch has not been pushed. The commands below are written to work
> against a published release once one is cut, and cannot be demonstrated against
> a live registry today. That is expected; these docs record the intended operator
> procedure, not a claim of existing published artifacts.

## Trust anchor

Every signature produced by the release pipeline is keyless — the signing
certificate is issued by Fulcio to the GitHub Actions OIDC identity of the
release workflow. The two values that fix this trust anchor are:

```
--certificate-oidc-issuer  https://token.actions.githubusercontent.com
--certificate-identity-regexp  ^https://github.com/Jibbscript/kube-policies/.github/workflows/release.yml@refs/tags/v.*$
```

The regexp matches any release tag (`refs/tags/v1.2.3`, etc.) and ties the
certificate to the exact workflow file. A signature issued from any other
workflow, fork, or branch will not match and `cosign verify` will fail.

---

## Quick start: verify-release.sh

The simplest path is to run the included script, which performs all checks in
one shot:

```bash
scripts/verify-release.sh v1.2.3
```

The script verifies, in order:

1. Container image signatures (`cosign verify`)
2. SBOM attestations (`cosign verify-attestation --type spdxjson`)
3. SLSA build provenance (`gh attestation verify`)
4. Binary and Helm chart blob signatures (`cosign verify-blob`)

It exits 0 only if every available check passes. The two images it checks are
`ghcr.io/jibbscript/kube-policies/admission-webhook` and
`ghcr.io/jibbscript/kube-policies/policy-manager`.

Override the repo or registry with environment variables:

```bash
REPO=owner/fork REGISTRY=ghcr.io scripts/verify-release.sh v1.2.3
```

## Step-by-step verification

### 1. Container image signatures

Images are signed by digest (not by mutable tag) in the
`sign-attest-provenance` job of `release.yml`.

```bash
VERSION=v1.2.3
OIDC_ISSUER="https://token.actions.githubusercontent.com"
IDENTITY_REGEXP="^https://github.com/Jibbscript/kube-policies/.github/workflows/release.yml@refs/tags/${VERSION}$"

cosign verify \
  --certificate-identity-regexp "${IDENTITY_REGEXP}" \
  --certificate-oidc-issuer "${OIDC_ISSUER}" \
  "ghcr.io/jibbscript/kube-policies/admission-webhook:${VERSION}"

cosign verify \
  --certificate-identity-regexp "${IDENTITY_REGEXP}" \
  --certificate-oidc-issuer "${OIDC_ISSUER}" \
  "ghcr.io/jibbscript/kube-policies/policy-manager:${VERSION}"
```

Successful output includes a JSON block with `"issuer"` and `"subject"` fields
matching the values above, plus the SHA-256 digest of the signed image layer.

### 2. SBOM attestation

The SBOM is a SPDX-JSON document, cryptographically bound to each image digest
as a cosign attestation:

```bash
cosign verify-attestation \
  --type spdxjson \
  --certificate-identity-regexp "${IDENTITY_REGEXP}" \
  --certificate-oidc-issuer "${OIDC_ISSUER}" \
  "ghcr.io/jibbscript/kube-policies/admission-webhook:${VERSION}" \
  | jq '.payload | @base64d | fromjson | .predicate.name'
```

The `--type spdxjson` flag selects only the SPDX SBOM attestation; cosign
prints a JSON envelope per matching attestation. The SBOM is the
authoritative, registry-bound record; the loose `*-sbom.spdx.json` files
shipped as release assets are a convenience copy only.

### 3. SLSA build provenance

Provenance is generated by `actions/attest-build-provenance` and stored in
the GitHub Attestations API. The canonical verification tool is `gh`:

```bash
gh attestation verify \
  "oci://ghcr.io/jibbscript/kube-policies/admission-webhook:${VERSION}" \
  --repo Jibbscript/kube-policies

gh attestation verify \
  "oci://ghcr.io/jibbscript/kube-policies/policy-manager:${VERSION}" \
  --repo Jibbscript/kube-policies
```

Alternatively, verify the cosign-signed SLSA provenance directly:

```bash
cosign verify-attestation \
  --type slsaprovenance \
  --certificate-identity-regexp "${IDENTITY_REGEXP}" \
  --certificate-oidc-issuer "${OIDC_ISSUER}" \
  "ghcr.io/jibbscript/kube-policies/admission-webhook:${VERSION}"
```

### 4. Binary and Helm chart blob signatures

Each release asset ships alongside a `.sig` (detached signature) and `.pem`
(Fulcio certificate bundle). Download the release assets, then verify each
blob:

```bash
# Example: verify the Helm chart
ASSET="kube-policies-${VERSION#v}.tgz"

cosign verify-blob \
  --certificate "${ASSET}.pem" \
  --signature "${ASSET}.sig" \
  --certificate-identity-regexp "${IDENTITY_REGEXP}" \
  --certificate-oidc-issuer "${OIDC_ISSUER}" \
  "${ASSET}"
```

The same pattern applies to each binary (`admission-webhook-linux-amd64`,
`policy-manager-linux-amd64`, etc.) and to the `checksums.txt` manifests.
`verify-release.sh` automates this for any `*.tgz`, `admission-webhook-*`,
and `policy-manager-*` files found in the current directory.

### 5. Checksum verification

After verifying the blob signatures, cross-check against the `checksums.txt`
manifest:

```bash
sha256sum --check checksums.txt
```

## Rekor transparency-log lookup

Every keyless signature is logged immutably in the Rekor public-good
transparency log. To retrieve the log entry for an image signature:

```bash
# Get the digest of the signed image
DIGEST=$(cosign triangulate \
  "ghcr.io/jibbscript/kube-policies/admission-webhook:${VERSION}" \
  --type digest)

# Search Rekor for entries by subject digest
rekor-cli search --sha "${DIGEST}"
```

Or query the Rekor REST API directly:

```bash
curl -s "https://rekor.sigstore.dev/api/v1/index/retrieve" \
  -H "Content-Type: application/json" \
  -d "{\"hash\": \"sha256:${DIGEST#sha256:}\"}" \
  | jq '.'
```

The log entry includes the signed payload, the Fulcio certificate (with the
workflow OIDC SAN), the inclusion proof, and a signed tree hash. This provides
tamper-evidence independent of the container registry.

## What is NOT verified by these commands

- Admission-time enforcement of image signatures inside the cluster is a
  separate concern. See `docs/supply-chain/chart-verification.md` for
  chart-level verification and `docs/policies/image-signing.md` for
  in-cluster admission-time enforcement.
- Vulnerability scan results are captured at release time; see
  `docs/supply-chain/vuln-exception-process.md` for the suppression policy.
